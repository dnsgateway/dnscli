# 02: Namecheap Changeset Apply

**What to build:** A user can add, modify and delete Records in a Namecheap Zone, and apply Templates to it, through the usual Changeset preview and Safe Apply. Namecheap's `setHosts` replaces a domain's whole host list, so Apply re-reads that list, applies the Changeset to it, and writes the full result in one call. Every host and setting the user did not change survives, and a Changeset succeeds or fails as a whole. Covers user stories 22–31 of the spec.

**Blocked by:** 01

**Status:** resolved

- [x] Apply first reads the current host list and `EmailType` with getHosts. That read, not the cached Records, is what the changes are applied to
- [x] Each change's Before is matched by its content ProviderID (type, lower-cased name, TTL, value) when it has one, otherwise by (type, name, value). *(Was: by HostId; changed in review, see Comments.)* A Before that is not in the current list fails the whole Changeset with a conflict, and setHosts is not called
- [x] Adding or modifying a type other than A, AAAA, CNAME, MX, TXT and NS (not at the apex) fails the whole Changeset with a clear message before any request. SRV and CAA are refused until ticket 03 confirms their form shape; deleting them is allowed
- [x] The full resulting list goes in a single form-encoded POST of `namecheap.domains.dns.setHosts` (`HostName1`, `RecordType1`, `Address1`, `MXPref1`, `TTL1`, …) with the unchanged `EmailType`
- [x] Hosts the Changeset does not touch are sent back exactly as read, including URL, URL301, FRAME and ALIAS hosts with their TTLs and MX prefs
- [x] Every change shares the one call's result: all succeed, or Apply fails as a whole with Namecheap's error (returned as Apply's own error; see Comments). Results are in Changeset order
- [x] On success, each added or modified ChangeResult's Record is the Record as sent, with its content ProviderID, so it is cached without a Refresh
- [x] Adding or modifying an MX Record when the domain's EmailType is not MX fails the whole Changeset, after getHosts, with a message that the mail setting must be "Custom MX"; the EmailType is never changed
- [x] The "not supported yet" Apply from ticket 01 is gone
- [x] Seam 2 tests cover add, modify, delete and several changes at once, checking that setHosts received the full list with every untouched host (including a URL redirect) and the original EmailType; a rejected setHosts failing every change with its error; and an unsupported write type and a missing Before refused without calling setHosts

## Comments

- 2026-10-07: Implemented test-first (Seam 2, `internal/provider/namecheap/apply.go` and `apply_test.go`; the httptest fake now scripts setHosts, records what it received and can reject it).
  - Untouched hosts are resent from the raw getHosts answer: name, type, address (trailing dots kept), MXPref (also on non-MX hosts, as read) and TTL. A modified host keeps its place in the list; added hosts go at the end.
  - Added or modified Records: the name becomes relative (`@` for the apex, case kept), CNAME, NS and MX targets get a trailing dot (`.` stays `.`), MX splits `priority host` into MXPref and Address. Only MX hosts dnscli writes carry an MXPref; others leave it out. Confirm in ticket 03 that Namecheap accepts dotted targets and a missing MXPref.
  - Matching: a Before with a HostId matches only that host, and only if the host still reads with the same type, name and value; a host edited at Namecheap under the same HostId is a conflict too. A Before without a HostId matches the first unused host with the same type, name (case-insensitive) and value. Each host matches one change at most. TTL is not compared.
  - There is no typed conflict error in `provider`, so a missing Before fails every change with `namecheap: conflict, nothing was applied: <type> <name> <value> changed at Namecheap`, wrapping `provider.ErrNotFound` as GoDaddy does.
  - Type check runs before any request (not even getHosts). Writable: A, AAAA, CNAME, MX, TXT, CAA, and NS below the apex. Deleting any type, including URL redirects and SRV, is allowed. The error names every refused Record.
  - Apply never returns a top-level error: a failed getHosts, a refused type, a conflict, a malformed MX value, an `ERROR` answer to setHosts, or `IsSuccess="false"` each fail every change with the same error. An empty Changeset sends nothing.
  - On success an added or modified ChangeResult's Record is `After` with its ProviderID cleared, since setHosts gives every host a new HostId. The TUI then counts it as not cached and needs a Refresh, as the spec accepts.
  - Risk: every setHosts renumbers all hosts, so the cached HostIds of untouched Records go stale after any Apply. Until the next Refresh, Safe Apply's re-check (by ProviderID) reports those Records as conflicts. Refreshing after an Apply clears it. Fixing it without a Refresh needs a TUI or Store change, which this ticket rules out.
  - Risk (from the spec): an edit made at Namecheap between Apply's getHosts and its setHosts is lost. That gap is one round-trip.
- 2026-10-07: Review fixes (/code-review of 519d1fd):
  - **Content-based ProviderIDs (deviation from the spec and ticket 01, by the user's decision).** A Record's ProviderID is now its type, lower-cased name, TTL and value, as GoDaddy's is (`withID`), on read and on every Apply result. HostId is no longer used. Why: setHosts renumbers every host, so after a deletion-only Apply the TUI kept stale HostIds. The next Safe Apply reported false conflicts, and "apply over" then dropped deletions and turned edits into duplicate additions. Apply matches a Before by that content ID (TTL included), or by type, name and value when it has none. Added and modified results are the host as sent, read back the way Records reads it (so `10\tmx.example.net` comes back as `10 mx.example.net`), with its content ID, so the TUI caches them without a Refresh. This replaces the "Risk: cached HostIds go stale" note above. The spec's Records and Apply bullets are amended.
  - **CAA writes are refused** until ticket 03 confirms Namecheap's setHosts encoding for CAA, like SRV. Adding or modifying CAA fails the Changeset before any request; deleting CAA is allowed. A follow-up enables CAA (and SRV) once ticket 03 confirms them.
  - **MX needs the "Custom MX" mail setting.** When the domain's EmailType (from Apply's getHosts read) is not MX (FWD, MXE, OX, empty, …), Namecheap ignores MX hosts, so adding or modifying an MX Record fails the Changeset. The message says to set the domain's mail setting to "Custom MX" in Namecheap's console. EmailType is still sent back unchanged (story 28). Deleting MX Records is allowed whatever the EmailType.
  - **MX value parsing** uses `strings.Fields` and needs exactly two fields, priority (0–65535) and host, like `godaddy.toWire`. `10 mx.example.net extra` is refused now; any whitespace separates the fields.
  - **"Nothing was applied" is Apply's own error.** The TUI (`internal/tui/apply.go`) takes a non-nil error from `Apply` as "Could not apply the changes to <zone>: …": every change stays pending, nothing is cached, no serial poll. Per-change errors instead read "Applied 0 of N changes; N failed …" and go through the partial-apply path. Cloudflare and GoDaddy return per-change errors because their changes really succeed or fail one by one; the fake Provider returns a top-level error when nothing could be applied. So every whole-Changeset failure now returns `ApplyResult{}` and an error: a refused type, a mail setting that isn't Custom MX, a malformed MX value, a conflict, a failed getHosts (including unauthorized and rate limited), and a rejected setHosts. Errors stay typed (`errors.Is` ErrNotFound for a conflict, ErrUnauthorized, ErrRateLimited). An `ERROR` answer to setHosts says "nothing was applied". A transport failure, a non-2xx status or `IsSuccess="false"` says Namecheap may or may not have applied the changes and to Refresh. The TUI's conflict path (automatic Refresh plus "apply over") only follows its own re-check, so a conflict that only Apply's read finds can't take it without a TUI change. Its message instead tells the user to Refresh and review. This narrows story 29: Namecheap's message is shown once for the Changeset, not once per change.
  - `relative` is now `provider.RelativeName` in `internal/provider/names.go`, next to `AbsoluteName`, and both GoDaddy and Namecheap use it. GoDaddy's behaviour is unchanged.
  - Not fixed: each Safe Apply reads getHosts twice, once for the TUI's re-check and once for Apply's own read. Both are kept for safety: Apply's read is the list setHosts replaces, and it keeps the gap before the write to one round-trip.
